# Black Friday Shopping Rush — Triton on ROCm demo

A demo showing that Triton Inference Server, running on ROCm, sustains
5X more inference throughput at peak traffic without added infrastructure
and without giving up latency. A CTR (click-through-rate) recommendation
model is the example workload used to make the traffic relatable; the
actual subject of the demo is the serving stack's behavior under light
vs. heavy load.

## Folder structure

```
triton-black-friday-demo/
├── app.py                        Flask backend + bridge to Triton
├── requirements.txt
├── README.md                     this file
├── static/
│   └── index.html                the UI (served by app.py)
├── triton_repo/
│   └── ctr_recommender/
│       ├── config.pbtxt          dynamic_batching, instance_group, ROCm accelerator
│       └── 1/                    put model.onnx here (see below)
└── scripts/
    ├── export_dummy_model.py     generates a placeholder ONNX model
    ├── launch_triton.sh          convenience wrapper around tritonserver
    └── triton_ctr_load_test.py  standalone CLI load-test client
```

## Two ways to run this

### A. Rehearsal mode — no GPU host needed

If you just want to walk through the UI (e.g. to rehearse the demo or
show someone the concept), you don't need Triton or a GPU at all:

```bash
python -m venv venv && source venv/bin/activate      # optional
pip install -r requirements.txt
python app.py
```

Open `http://localhost:5000`. Since no Triton server is reachable at
`localhost:8000`, the backend automatically falls back to **simulated
mode** — the mode pill in the header will show "SIMULATED (no Triton
reachable)" and the dashboard runs the same scripted light-to-heavy ramp
as before, so every screen still works for a walkthrough. Nothing about
this mode is secretly live; the disclaimer bar and mode pill make that
explicit.

### B. Live mode — real numbers from an AMD Instinct GPU host

1. **Get a model into the repository.** If you don't have a real trained
   CTR model handy yet, generate a placeholder (untrained, random
   weights — exists purely to exercise the pipeline):

   ```bash
   pip install torch onnx
   python scripts/export_dummy_model.py
   ```

   This writes `triton_repo/ctr_recommender/1/model.onnx`. To use a real
   model instead, export it to ONNX yourself with input tensor `INPUT`
   (shape `[batch, 32]`, FP32) and output tensor `OUTPUT` (shape
   `[batch, 1]`, FP32) — or edit `config.pbtxt` to match your model's
   actual signature, and update `app.py`'s `NUM_FEATURES` /
   `INPUT_NAME` / `OUTPUT_NAME` env vars to match.

2. **Launch Triton on the ROCm host**, with the model repository
   mounted. This must be run somewhere with AMD Instinct GPUs and ROCm
   installed, and Docker (or podman) available:

   ```bash
   chmod +x scripts/launch_triton.sh   # zip extraction can drop the +x bit
   docker pull rocm/tritoninferenceserver:tritoninferenceserver-25.12.amd1_rocm7.2_ubuntu24.04_py3.12
   ./scripts/launch_triton.sh
   ```

   This runs that image in a container with `/dev/kfd` and `/dev/dri`
   passed through, mounts `triton_repo/` into it, and starts
   `tritonserver` with the ROCm execution provider enabled. Override the
   image or switch to podman without editing the script:

   ```bash
   CONTAINER_RUNTIME=podman TRITON_IMAGE=my-registry/my-triton-rocm:tag ./scripts/launch_triton.sh
   ```

3. **Run the backend**, pointed at that Triton instance:

   ```bash
   pip install -r requirements.txt
   TRITON_HTTP_URL=<triton-host>:8000 python app.py
   ```

   (If `app.py` and Triton are on the same machine, the default
   `localhost:8000` just works.)

4. Open `http://localhost:5000`. Once the backend's periodic readiness
   check confirms Triton is up and the model is loaded, the mode pill
   flips to "LIVE — Triton on ROCm" and every number on the dashboard
   (throughput, P50/P99, batch size estimate, queue depth, GPU
   utilization where available) comes from real measured traffic
   generated by `app.py`'s own worker-thread pool — not a script.

5. Click **Start the rush** to ramp the load from light (~300 simulated
   concurrent shoppers) to heavy (~4,800). Internally this scales a
   bounded pool of real client threads (see `LIVE_MAX_WORKERS` /
   `SHOPPER_TO_WORKER_RATIO` below) that keep Triton genuinely busy —
   it does not spawn one OS thread per shopper, which would be
   impractical on a demo laptop; see "Honesty notes" below.

## Standalone load-test client

`scripts/triton_ctr_load_test.py` is independent of `app.py` — a CLI
tool for driving load against Triton directly and printing a
light-vs-heavy comparison table, useful for benchmarking outside of the
UI or for gathering real numbers to put into a slide:

```bash
python scripts/triton_ctr_load_test.py --url localhost:8000 \
    --model-name ctr_recommender --compare --duration 30
```

## Configuration (environment variables for app.py)

| Variable | Default | Meaning |
|---|---|---|
| `TRITON_HTTP_URL` | `localhost:8000` | Triton's HTTP endpoint |
| `TRITON_METRICS_URL` | derived, port 8002 | Triton's Prometheus metrics endpoint |
| `MODEL_NAME` | `ctr_recommender` | Model to probe/infer against |
| `MODEL_VERSION` | `""` (latest) | |
| `INPUT_NAME` / `OUTPUT_NAME` | `INPUT` / `OUTPUT` | Must match your `config.pbtxt` |
| `NUM_FEATURES` | `32` | Input feature vector width |
| `BASELINE_SHOPPERS` / `HEAVY_SHOPPERS` | `320` / `4800` | Light / heavy target load levels shown in the UI |
| `LIVE_MAX_WORKERS` | `64` | Hard cap on real client threads spawned in live mode |
| `SHOPPER_TO_WORKER_RATIO` | `50` | How many "shoppers" one real worker thread represents |
| `USE_ROCM_SMI` | `0` | Set to `1` to try `rocm-smi --showuse --json` locally for GPU utilization (only works if `app.py` runs on the GPU host itself) |
| `PORT` | `5000` | Port app.py listens on |

## Honesty notes (please read before presenting this)

- **"Concurrent shoppers" is a target load level, not a literal thread
  count.** In live mode, `app.py` runs a bounded pool of real worker
  threads (capped by `LIVE_MAX_WORKERS`) that continuously send genuine
  inference requests — it does not open 4,800 real OS connections on a
  demo laptop. The throughput/latency numbers that come back are real
  measurements of Triton under that bounded, but genuine, concurrent
  load.
- **GPU utilization has three possible sources**, shown next to the
  stat so it's never ambiguous: `rocm-smi` (most reliable, requires
  `app.py` to run on the GPU host with `USE_ROCM_SMI=1`), `triton-metrics`
  (scraped from Triton's `/metrics` endpoint — availability depends on
  your Triton build/version), or `estimated` (a load-based approximation
  used only when neither real source is available, so the dashboard
  doesn't show a blank stat).
- **Batch size and queue depth in live mode** are derived from Triton's
  own Prometheus counters (`nv_inference_exec_count`,
  `nv_inference_request_success`, `nv_inference_pending_request_count`).
  If your Triton build doesn't expose these metrics, those fields will
  fall back to the same estimate used in simulated mode.
- **The dummy ONNX model has random, untrained weights.** It's there so
  the whole pipeline (config → load → infer → measure) is runnable
  before you have a real model. Its predictions are meaningless; only
  use it for exercising the serving infrastructure, not for anything
  resembling a real CTR evaluation.
- **The UI is a custom-built demo page, not an existing AMD product.**
  A disclaimer to that effect is shown in the app itself — please keep
  it there if you adapt this for a live audience.
